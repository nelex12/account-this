# Замечания к API, найденные при проектировании интерфейса

Сверялся с `backend/AccountThis.Api/api.yaml` (v2.3.0) и документом «Описание проекта подробно…».
Код бэкенда не менял. Макеты сделаны строго в рамках текущего контракта; ниже — места, где интерфейсу
пришлось обходиться без данных, и вопросы, которые стоит решить.

## Не хватает данных

1. **Нет «кто я».** В JWT только `sub` и `role`, эндпоинта вида `GET /api/auth/me` нет.
   Сотрудник узнаёт своё ФИО только из сертификата, владелец — из `GET /api/users`, а **завхоз не может узнать своё имя вовсе**.
   В макетах у завхоза вместо имени показан номер телефона, с которым он вошёл (`09-issuer-shift-desktop`).
   Предложение: claim `name` в JWT или `GET /api/auth/me → UserResponse`.
2. **Имена завхозов в журнале.** `RentalLogEntry` содержит только `issuerId`, а `GET /api/users` доступен лишь владельцу.
   Завхоз видит коллег как «Завхоз № 3» (`24-journal-details`). Предложение: поле `issuerName`.
3. **Причина 403 при входе — только текстом.** «Не подтверждён» и «уволен» различаются лишь по `detail`.
   Интерфейс оформляет их по-разному (ожидание — жёлтым, отказ — нейтрально), для этого нужен машинный код:
   своё значение `type` или поле-расширение ProblemDetails, например `"reason": "NOT_APPROVED" | "DEACTIVATED"`.
   То же для 403 на `/api/auth/worker-cert`.
4. **Журнал без фильтров по времени и без постраничности.** `GET /api/logs` фильтрует только по `action` и `toolId`.
   Период, флаг и сотрудник в макетах фильтруются на клиенте по полному журналу, который будет только расти.
   Предложение: `from`, `to`, `workerId`, `flag` (или группа флагов) и `limit` + курсор.
5. **Списанные инструменты не получить списком.** `GET /api/tools` отдаёт только активные; списанный виден лишь по id.
   Архива списаний в интерфейсе поэтому нет. Предложение: `GET /api/tools?includeInactive=true`.
6. **В `UserResponse` нет даты регистрации** — заявки нельзя упорядочить «сначала старые». Предложение: `createdAt`.
7. **Сотрудник не видит, что у него на руках.** Роли Worker недоступны `/api/tools` и `/api/logs`.
   Частый вопрос сотрудника в конце смены остаётся без ответа. Предложение: `GET /api/tools?holderId=me` для Worker.
8. **Нельзя описать повреждение при возврате.** В `RentalOperation` нет комментария, поэтому «что именно сломано»
   завхоз дописывает потом через `PATCH`. Если добавлять поле, оно войдёт в подписанную операцию и увеличит QR-код.

## Поведение, о котором стоит договориться

9. **Отказ в заявке = увольнение.** Отдельного «отклонить» нет, поэтому отказ делается через `DELETE /api/users/{id}`,
   и номер телефона остаётся занят навсегда. В диалоге отказа это прямо сказано (`29-users-dialogs`).
   Если это нежелательно — нужен отдельный статус «заявка отклонена» с освобождением номера.
10. **Нет смены и сброса пароля.** Ошибка в пароле при регистрации означает потерянный аккаунт и занятый номер.
    В форме регистрации пароль вводится дважды и есть предупреждение (`04-register`). Требований к паролю в контракте нет
    (`minLength`) — стоит зафиксировать, чтобы клиент и сервер проверяли одинаково.
11. **Роль «Владелец» можно запросить при регистрации.** Интерфейс выделяет такие заявки и подтверждает их отдельным диалогом.
    Возможно, стоит вообще не предлагать эту роль в форме.
12. **Неучтённый возврат оставляет инструмент «на руках».** Если возврат пришёл с флагом (например `TIME_DRIFT`),
    держатель не меняется, а ручного способа поправить его нет — только новый QR-код от сотрудника.
    Интерфейс подсказывает это в разборе записи; возможно, владельцу нужна ручная корректировка.
13. **Уведомлений нет.** Владелец узнаёт о новых заявках по счётчику в меню, сотрудник о подтверждении — попыткой войти.

## Решения за фронтендом (сервер не затрагивают)

14. **Формат QR на наклейке инструмента.** По документу его задаёт фронтенд. Предлагаю строгий, как у AT1:
    `AT1T.<toolId>.<base64url(название UTF-8)>` — однозначно разбирается и не путается с QR сотрудника
    (приложение сотрудника на экране `06-worker-scan` отличает одно от другого).
15. **Проверки завхоза сверх контракта** — только предупреждения, сервер их не повторяет:
    состояние отличается от реестра; инструмента нет в реестре устройства; порядок операций по данным устройства
    (возврат уже принят, инструмент числится у другого) — `12-issuer-verify-warnings`.
16. **Работа с истёкшим JWT без сети.** Сканировать и проверять QR можно без входа (нужны ключ сервера и реестр),
    вход требуется только для отправки. Макет `08-issuer-shift-phone`, вариант «Вход истёк».
17. **Камера и оффлайн требуют HTTPS** (или localhost) — это в документе есть; на макетах показан экран «Нет доступа к камере».
