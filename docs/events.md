# События RabbitMQ — аудит и уведомления

Контракт сообщений между backend и RabbitMQ, как `api.yaml` для HTTP. При расхождении кода и этого файла ориентироваться на здравый смысл и менять в соответствии с бизнес—логикой или стандартными подходами.

## Зачем

После значимого действия API фиксирует событие «кто, что и когда сделал» и отправляет его в RabbitMQ.
Что делать с событием, решают потребители — отдельный процесс `AccountThis.Worker`:

- **audit** — складывает все события в журнал `audit_events`;
- **notifications** — выбирает то, что требует внимания Owner, и создаёт уведомления (`GET /api/notifications`).

Что даёт брокер:

- **API не зависит от потребителей.** HTTP-ответ не ждёт ни журнала, ни уведомлений. Worker можно остановить,
  обновить или перезапустить: события подождут в очередях и будут обработаны, когда он вернётся.
- **Новая реакция на события не меняет API.** Новый потребитель — новая очередь с подпиской на нужные
  routing key (`RabbitMqTopology.Queues`) и класс в Worker. Так добавлены уведомления: ни один сервис API для этого
  не менялся. Следующие кандидаты: отправка уведомлений во внешний канал (почта, мессенджер), отчёты и статистика.
- **Масштабирование и отказоустойчивость.** Медленный или упавший потребитель не тормозит остальных
  (у каждого своя очередь). Нескольких экземпляров Worker брокер нагружает по очереди.
- **Ничего не теряется.** Событие записывается в БД в той же транзакции, что и изменение (outbox), брокер хранит
  сообщения на диске, потребитель подтверждает сообщение только после записи, а необработанное откладывает
  в очередь отказов.

Синхронизация `/api/sync` через очередь **не** идёт: клиенту завхоза нужен ответ сразу — `logId`
и флаг по каждой записи, а также номера записей с ошибкой формата (400). Очередь не уменьшила бы работу БД,
только отложила бы её. В поток событий синхронизация попадает одним событием на запрос, а не на каждую запись.

## Путь события

```
сервис API ── INSERT outbox_events + NOTIFY (в транзакции изменения) ──► PostgreSQL
OutboxDispatcher (API) ── LISTEN / раз в 5 с ── читает outbox ──► exchange accountthis.events ── удаляет из outbox
   ├─ очередь audit         ──► AuditConsumer (Worker)         ──► audit_events
   └─ очередь notifications ──► NotificationsConsumer (Worker) ──► notifications ──► GET /api/notifications (API)
```

## Топология

| Объект | Имя | Параметры |
|---|---|---|
| Exchange | `accountthis.events` | `topic`, durable |
| Очередь | `audit` | durable, привязка `#` (все события), `x-dead-letter-exchange: accountthis.events.dlx` |
| Очередь | `notifications` | durable, привязки `user.registered`, `user.approved`, `user.deactivated`, `auth.session_reuse_detected`, `rental.synced`; `x-dead-letter-exchange: accountthis.events.dlx` |
| Exchange для отказов | `accountthis.events.dlx` | `fanout`, durable |
| Очередь отказов | `events.dead` | durable, привязана к `accountthis.events.dlx`; общая для всех потребителей |

Топология описана в одном месте — `AccountThis.Shared/Events/RabbitMqTopology.cs` — и объявляется идемпотентно
и отправителем, и потребителями при каждом подключении (`ExchangeDeclare`, `QueueDeclare`, `QueueBind`
с одинаковыми параметрами ничего не ломают при повторе). Отправитель объявляет и очереди: событие,
отправленное, пока Worker не запущен, ждёт в очереди, а не теряется.
Routing key сообщения — тип события (`user.deactivated`).

Очередь отказов раньше называлась `audit.dead`. В брокере, запущенном до переименования, она остаётся
привязанной к `accountthis.events.dlx` и тоже получает отказы; её можно удалить в веб-интерфейсе.

## Сообщение

Свойства AMQP: `content_type = application/json`, `delivery_mode = 2` (persistent — переживает перезапуск
брокера), `message_id = eventId`, `type = type`. Тело — JSON в UTF-8:

```json
{
  "eventId": "0b8f3c2e-6a1d-4e7b-9c55-2f1a7d3e8b40",
  "type": "user.deactivated",
  "occurredAt": 1790000000,
  "companyId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "actorId": "3f2b8c1e-5d4a-4c2b-9e7f-1a2b3c4d5e6f",
  "data": { "userId": "5a1d9e3b-2c4f-4b6a-8d7e-9f0a1b2c3d4e", "revokedSessions": 2 }
}
```

- `eventId` — UUID, новый для каждого события; по нему потребители отсекают повторную доставку.
- `occurredAt` — Unix time в секундах (время сервера в момент изменения), как везде в API.
- `companyId` — компания, в которой произошло событие; `actorId` — пользователь, чьё действие его породило.
- Имена полей — camelCase, как в `api.yaml`; id — UUID в каноническом виде.
- Конверт (класс `EventMessage`) общий для API и Worker — проект `AccountThis.Shared`.

## Типы событий

Событие создаётся, только если состояние действительно изменилось: повторное подтверждение, увольнение
или списание (200 без изменений) события не создаёт. Неудачные запросы (4xx) событий не создают.

| type | Когда | actorId | data |
|---|---|---|---|
| `user.registered` | `POST /api/auth/register` → 201 | новый пользователь | `userId`, `role` |
| `user.approved` | `POST /api/users/{id}/approve`, был не подтверждён | Owner | `userId` |
| `user.deactivated` | `DELETE /api/users/{id}`, был активен | Owner | `userId`, `revokedSessions` — сколько сессий погашено |
| `auth.logged_in` | `POST /api/auth/login` → 200 | вошедший | `{}` |
| `auth.session_reuse_detected` | `/api/auth/refresh`: предъявлен погашенный ротацией токен живой сессии | владелец сессии | `{}` |
| `tool.created` | `POST /api/tools` → 201 | вызывающий | `toolId`, `name` |
| `tool.updated` | `PATCH /api/tools/{id}` → 200 | вызывающий | `toolId` и переданные поля: `condition`, `comment` |
| `tool.written_off` | `DELETE /api/tools/{id}`, был активен | Owner | `toolId` |
| `rental.synced` | `POST /api/sync` → 200, сохранена хотя бы одна новая запись (только повторная отправка события не создаёт) | завхоз | `total` — записей в запросе, `created` — новых (без повторной отправки), `flags` — число новых записей по флагам: `{"VALID": 3, "TIME_DRIFT": 1}` |

Обновления refresh token и выход в события не попадают — их слишком много, а пользы мало.
Телефоны, пароли и токены в события не попадают никогда.

## Отправитель (API): transactional outbox

- Сервис записывает событие в таблицу `outbox_events` **в той же транзакции**, что и само изменение
  (`IEventOutbox.AddAsync`). Откатилось изменение — откатилось и событие; зафиксировано — событие точно уйдёт.
  Событий о том, чего не было, и потерянных событий о том, что было, не бывает.
- В той же транзакции выполняется `NOTIFY outbox_events`. PostgreSQL доставляет его только после COMMIT,
  поэтому фоновая служба `OutboxDispatcher` (`LISTEN outbox_events`) отправляет событие сразу после фиксации.
  Раз в 5 секунд она проверяет outbox и без сигнала: так уходят события, оставшиеся после остановки
  приложения или недоступности брокера.
- Отправка пачками до 100 событий по порядку `id`, с publisher confirms: запись удаляется из outbox только после
  того, как брокер подтвердил приём. `FOR UPDATE SKIP LOCKED` — несколько экземпляров API не отправят одно событие
  одновременно.
- Брокер недоступен — HTTP-ответы не меняются, события копятся в outbox, в лог сервера (`ILogger`, Warning)
  пишется причина; когда брокер вернётся, всё накопленное будет отправлено.
- Доставка «хотя бы один раз»: при сбое между подтверждением брокера и удалением из outbox событие будет
  отправлено повторно. Поэтому каждый потребитель обрабатывает событие с тем же `eventId` один раз.

## Потребители (AccountThis.Worker)

Отдельный процесс (`backend/AccountThis.Worker`, в Docker — сервис `worker`). С API у него общие только БД и брокер.
Таблицы создают миграции API.

Общее для всех потребителей (`EventConsumer`):

- `BackgroundService`, своё соединение и канал на очередь, `prefetch = 10`, переподключение при обрыве.
- Подтверждение вручную (`autoAck: false`): `BasicAck` только после записи в БД. Упал до ack — брокер
  доставит сообщение снова, поэтому обработка идемпотентна (`ON CONFLICT (event_id) DO NOTHING`).
- Тело не разбирается как конверт или в `data` нет нужных потребителю полей — `BasicNack(requeue: false)`:
  сообщение уходит в `events.dead` для разбора, а не крутится в очереди вечно. Так же — ошибка данных
  от PostgreSQL (классы SQLSTATE 22 и 23): повтор её не исправит.
- Временная ошибка БД (нет связи, ещё не применены миграции) — `BasicNack(requeue: true)` через секунду:
  сообщение вернётся в очередь и будет обработано позже.
- Любая другая ошибка обработчика (ошибка в коде) — тоже `BasicNack(requeue: false)` в `events.dead`:
  сообщение не остаётся неподтверждённым и не занимает место `prefetch`.

### Потребитель `audit`

Все события → `audit_events` как есть (тип, компания, автор, время, `data`). Журнал для разбора инцидентов:
кто подтвердил, уволил, списал, когда был вход.

### Потребитель `notifications`

Уведомления Owner → `notifications` (читает API: `GET /api/notifications`, `POST /api/notifications/{id}/read`).

| Событие | Что делает |
|---|---|
| `user.registered`, роль Worker или Issuer | уведомление `EmployeeAwaitingApproval` о новом пользователе |
| `user.approved`, `user.deactivated` | уведомление `EmployeeAwaitingApproval` об этом пользователе становится прочитанным — решение принято |
| `auth.session_reuse_detected` | уведомление `SessionReuseDetected` о владельце сессии |
| `rental.synced`, среди новых записей есть флаги кроме VALID | уведомление `SuspiciousSync` о завхозе, в `flags` — число таких записей по флагам |

Регистрация Owner и синхронизация только VALID-записей уведомлений не создают.

## Настройки

Переменные окружения (`.env`, см. `env.example`): `RABBITMQ_HOST`, `RABBITMQ_PORT`, `RABBITMQ_USER`,
`RABBITMQ_PASSWORD` и `POSTGRES_*` — одинаковые для API и Worker. Веб-интерфейс брокера (очереди, сообщения,
отказы) — http://localhost:15672.

## Тесты

Интеграционные тесты поднимают PostgreSQL и RabbitMQ в Testcontainers, API (`WebApplicationFactory`) и Worker
(отдельный хост с теми же потребителями, `AddAccountThisWorker`). Тест выполняет действие через API и ждёт строку
в `audit_events` или уведомление в `GET /api/notifications` (с таймаутом: обработка асинхронная).
