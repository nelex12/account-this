# События RabbitMQ — журнал аудита

Контракт сообщений между backend и RabbitMQ, как `api.yaml` для HTTP. При расхождении кода и этого файла прав этот файл.

## Зачем

Backend после значимых действий публикует событие «кто, что и когда сделал». Потребитель очереди `audit`
складывает события в таблицу `audit_events` (схема — `database/init.sql`). HTTP-запрос не ждёт записи
в журнал и не падает, если журнал недоступен: это и даёт очередь.

Синхронизация `/api/sync` через очередь **не** идёт: клиенту завхоза нужен ответ сразу — `logId`
и флаг по каждой записи, а также номера записей с ошибкой формата (400). Очередь не уменьшила бы работу БД,
только отложила бы её. В журнал аудита синхронизация попадает одним событием на запрос, а не на каждую запись.

## Топология

| Объект | Имя | Параметры |
|---|---|---|
| Exchange | `accountthis.events` | `topic`, durable |
| Очередь | `audit` | durable, привязка `#` (все события), `x-dead-letter-exchange: accountthis.events.dlx` |
| Exchange для отказов | `accountthis.events.dlx` | `fanout`, durable |
| Очередь отказов | `audit.dead` | durable, привязана к `accountthis.events.dlx` |

Объявление идемпотентно: и издатель, и потребитель при старте объявляют то, что используют
(`ExchangeDeclare`, `QueueDeclare`, `QueueBind` с одинаковыми параметрами ничего не ломают при повторе).
Routing key сообщения — тип события (`user.deactivated`), поэтому новые потребители могут подписаться
только на нужное: `user.*`, `rental.synced`.

## Сообщение

Свойства AMQP: `content_type = application/json`, `delivery_mode = 2` (persistent — переживает перезапуск
брокера), `message_id = eventId`, `type = type`. Тело — JSON в UTF-8:

```json
{
  "eventId": "0b8f3c2e-6a1d-4e7b-9c55-2f1a7d3e8b40",
  "type": "user.deactivated",
  "occurredAt": 1790000000,
  "companyId": "7c9e6679-7425-40de-944b-e07fc1f90ae7",
  "actorId": "3f2b8c1e-5d4a-4c2b-9e7f-1a2b3c4d5e6f",
  "data": { "userId": "5a1d9e3b-2c4f-4b6a-8d7e-9f0a1b2c3d4e", "revokedSessions": 2 }
}
```

- `eventId` — UUID, новый для каждого события; по нему потребитель отсекает повторную доставку.
- `occurredAt` — Unix time в секундах (время сервера), как везде в API.
- `companyId` — компания, в которой произошло событие; `actorId` — пользователь, чьё действие его породило.
- Имена полей — camelCase, как в `api.yaml`; id — UUID в каноническом виде.

## Типы событий

Событие публикуется, только если состояние действительно изменилось: повторное подтверждение, увольнение
или списание (200 без изменений) события не создаёт. Неудачные запросы (4xx) событий не создают.

| type | Когда | actorId | data |
|---|---|---|---|
| `user.registered` | `POST /api/auth/register` → 201 | новый пользователь | `userId`, `role` |
| `user.approved` | `POST /api/users/{id}/approve`, был не подтверждён | Owner | `userId` |
| `user.deactivated` | `DELETE /api/users/{id}`, был активен | Owner | `userId`, `revokedSessions` — сколько сессий погашено |
| `auth.logged_in` | `POST /api/auth/login` → 200 | вошедший | `{}` |
| `auth.session_reuse_detected` | `/api/auth/refresh`: предъявлен погашенный ротацией токен живой сессии | владелец сессии | `{}` |
| `tool.created` | `POST /api/tools` → 201 | вызывающий | `toolId`, `name` |
| `tool.updated` | `PATCH /api/tools/{id}` → 200 | вызывающий | `toolId` и переданные поля: `condition`, `comment` |
| `tool.written_off` | `DELETE /api/tools/{id}`, был активен | Owner | `toolId` |
| `rental.synced` | `POST /api/sync` → 200 с непустым массивом | завхоз | `total` — записей в запросе, `created` — новых (без повторной отправки), `flags` — число новых записей по флагам: `{"VALID": 3, "TIME_DRIFT": 1}` |

Обновления refresh token и выход в журнал не попадают — их слишком много, а пользы мало.
Телефоны, пароли и токены в события не попадают никогда.

## Издатель (backend)

- Публикует **после** фиксации транзакции: событие о том, что откатилось, — ложь в журнале.
- Включены publisher confirms: `BasicPublishAsync` завершается, когда брокер принял сообщение.
- Ошибка публикации (брокер недоступен) записывается в лог сервера (`ILogger`, уровень Warning) и **не**
  меняет HTTP-ответ: действие уже выполнено и зафиксировано.
- Сознательное упрощение: при сбое между COMMIT и публикацией событие теряется. Надёжный вариант —
  transactional outbox (событие пишется в таблицу в той же транзакции, отдельный фоновый процесс
  переносит его в RabbitMQ); можно сделать позже, контракт сообщений при этом не меняется.

## Потребитель `audit`

- `BackgroundService` в том же приложении; одно соединение, свой канал, `prefetch = 10`.
- Подтверждение вручную (`autoAck: false`): `BasicAck` только после записи в БД. Упал до ack — брокер
  доставит сообщение снова, поэтому вставка идемпотентна: `INSERT ... ON CONFLICT (event_id) DO NOTHING`.
- Тело не разбирается или нет обязательных полей — `BasicNack(requeue: false)`: сообщение уходит в `audit.dead`
  для разбора, а не крутится в очереди вечно.
- Ошибка БД — `BasicNack(requeue: true)`: сообщение вернётся в очередь и будет обработано позже.

## Настройки

Переменные окружения (`.env`, см. `env.example`): `RABBITMQ_HOST`, `RABBITMQ_PORT`, `RABBITMQ_USER`,
`RABBITMQ_PASSWORD`. Веб-интерфейс брокера (очереди, сообщения, отказы) — http://localhost:15672.
